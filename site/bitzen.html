Bitcoin in ZP

A contract on the ZP testnet follows Bitcoin's block chain by itself. It checks every block header it is given: the proof of work, Bitcoin's difficulty rule and which branch has more work. Nobody has to be trusted to tell it what happened on Bitcoin.

How it works

  • Headers in, checked on the chain. A relayer sends each new Bitcoin block header to the contract. The contract checks that it points to the previous block, that its proof of work is valid, and that it carries the right difficulty, including Bitcoin's retarget every 2,016 blocks.
  • Forks. When Bitcoin switches to a branch with more work, the relayer sends that branch from the last common block, and the contract replaces its tip only if the branch is really longer.
  • No trust in the relayer. The relayer cannot make the contract accept a header that is not a valid Bitcoin block. Anyone can run another relayer; the contract takes headers from anyone.
  • No custody. The contract holds no bitcoin. It is the base for proving a Bitcoin payment inside ZP, so that ZP assets can be exchanged for bitcoin without a middleman.

Limits of this test

  • It runs on the ZP testnet; it follows Bitcoin's main chain, whose headers are public.
  • A branch must stay inside one 2,016-block difficulty period and be at most 6 blocks long; a deeper reorganisation is out of scope (a payment is accepted only after 6 confirmations).
  • The contract starts from a checkpoint, a recent block given at the start, as any light client does.
  • Payment proofs and the swap come next; they need a protocol upgrade that is still being prepared.
